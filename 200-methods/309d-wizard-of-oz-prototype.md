# Wizard of Oz Prototype
**Tier:** 200 — Practice | **Arc:** 309 (Prototyping) | **Prereqs:** 177, 132 | **Wave:** 4

**Goal:** Run a Wizard of Oz prototype session that tests whether an automated system behavior would be valuable — before building the automation.

**Prior Knowledge Hook:** The model most people bring to prototyping AI or automated features: we need to build it (at least partially) before we can test it. The assumption is that the user experience of an automated feature requires the automation to be real. This is wrong in a specific and useful way: users don't experience the automation — they experience the *output* of the automation. The output can be human-generated in real time without the user knowing, and without the automation existing.

**Trigger:** Use this when prototyping any behavior that would, in production, be generated by a system — recommendations, AI-generated content, automated categorization, smart defaults, process automation, or any feature where "the system figures it out." Use it specifically when the cost of building the automation would be high and the value of the behavior is unproven.

**Why this works:** A Wizard of Oz prototype separates two questions that are usually conflated: "is this behavior valuable?" and "can we build this behavior?" The second question should never be answered until the first one is. Wizard of Oz answers the first question cheaply — a human produces the output in real time, hidden from the user, while the user experiences the interface as if it were automated. If users don't find the behavior valuable, the cost of building the automation was avoided. If they do, you have evidence to justify the build.

The mechanism: users evaluate the *utility* of a feature, not its implementation. An AI recommendation that a human typed five seconds ago has the same utility value to the user as one generated by a model. Their feedback tells you whether the recommendation category is useful, whether the format works, whether the timing is right — all the questions that matter before implementation. What it can't tell you is whether the automation will achieve the accuracy users found valuable in the human-generated version. That's the limit of the method.

**Method:**

**Step 1: Define what the system is "doing."** Write a one-sentence description of the automated behavior you're testing: what triggers it, what it produces, and when the user sees it. This is your production spec for the test session — the human operator will execute it.

**Step 2: Build the interface minus the automation.** Create the UI that would display the automated behavior — the recommendation panel, the smart default field, the generated content area. Leave the content empty or templated. The user will see a real interface; the "automation" will be human-filled in real time.

**Step 3: Assign a human operator.** The operator's job is to produce the automated output, on cue, as if it were the system. Before the session, brief the operator on what the "system" would produce given specific inputs. The operator watches the session (or receives a signal from the facilitator) and types or triggers the output at the right moment. The user never knows.

**Step 4: Run the session as a regular usability test.** The facilitator runs the session; the operator produces outputs. The user interacts with the interface normally.

**Step 5: Debrief on utility, not performance.** Ask the user: was this useful? Would you use it? What would make it more useful? Do not discuss implementation. The session is testing utility, not accuracy.

**Artifact:** A session recording and notes capturing user reactions to the automated behavior — whether they used it, whether it changed their behavior, what they wished it did differently. Combined with session notes from 3-5 sessions, this becomes the evidence base for the implementation decision.

**Watchout:** The failure mode that catches smart teams: testing the *accuracy* of the human-generated outputs rather than the *utility* of the behavior category. The operator tries too hard to produce "good" outputs — clever recommendations, accurate categorizations — and the sessions measure whether the AI would be accurate, not whether the feature would be valuable. Wizard of Oz tests value, not accuracy. A behavior category the user doesn't find valuable in ideal conditions won't be saved by accurate automation.

**Try This:** Take a feature on your current roadmap that involves any automated or AI-generated behavior. Before building it: identify what the human version of that behavior would look like. Could a person do it manually in real time, without the user knowing? If yes, you have a Wizard of Oz test available. Sketch what the session would look like — who the operator would be, what they'd produce, and what you'd ask the user.

**Proof:** The Wizard of Oz worked if you have a clear answer to: "Is this behavior valuable enough to build?" Either you found that users found it useful (and have specific feedback about what made it useful), or you found that they didn't engage with it in ways that suggest the behavior is valuable. The false positive: sessions where users said "yes that's useful" when asked but didn't actually use the feature during the session. Observed behavior takes precedence over stated preference. If they said it was useful but never interacted with it, the value is theoretical, not demonstrated.

**Take This Further:** In the next week, identify one more automated behavior in your product or roadmap. For each one, ask: what is the human version of this, and how would we test it before building? Write one sentence: what's the riskiest assumption this behavior is built on, and would a Wizard of Oz test surface evidence against it?

**After you've run this yourself:** AI can help you prepare the Wizard of Oz operator: describe the automation you're testing and ask for a decision tree of likely user inputs and the appropriate system outputs. The operator can use this as a quick-reference guide to produce realistic outputs consistently across sessions.

**What Next:** The Wizard of Oz tests system behaviors. For prototyping the end-to-end experience of AI-assisted conversations or voice interactions, read 309e (Conversational Prototype). For when you need higher fidelity to test interaction details, read 309f (High-Fidelity Prototype).
