# UX Metrics
**Tier:** 200 — Practice | **Arc:** Standalone | **Prereqs:** 113-defining-success | **Note:** Pairs with 135-leading-lagging-indicators, 209-design-decision-records, 305-generalized-did-it-work

**Goal:** After this piece, you will be able to name one measurable UX outcome that connects your design work to a business result — written before you build.

**Prior knowledge hook:** Think of the last time someone asked "did the redesign work?" and the honest answer was "we think so, but we don't have the numbers to prove it."

**Trigger:** you're being asked to justify a UX improvement in terms a business stakeholder will accept — or you want to know whether your design change actually moved anything.

**Why this works:** a metric defined before building is the only metric that can be wrong — and being wrong is the only feedback that changes your next decision. Metrics defined after the fact can always be interpreted as reasonable.

**Method:** Use the HEART framework — five categories of UX quality that map to measurable signals:

- **H — Happiness:** how users feel about the experience. Measured by satisfaction surveys, NPS, or post-task ratings.
- **E — Engagement:** how frequently and deeply users interact. Measured by session frequency, feature use rate, actions per session.
- **A — Adoption:** how many users are picking up new features. Measured by first-use rate, activation rate for new functionality.
- **R — Retention:** whether users come back. Measured by return rate, churn, 30/60/90-day active use.
- **T — Task Success:** whether users accomplish what they're trying to do. Measured by completion rate, error rate, time-on-task.

For each proposed design change: pick the one HEART category that most directly maps to the business outcome this work is supposed to improve. Define a baseline (what's the current number?) and a target (what would success look like?). Write both before building.

**Artifact:** one HEART metric with its category, baseline, and target — written before the work starts, so the result is testable rather than interpreted.

**Watchout:** the most available metric isn't always the most useful one. If the only number you can get is page views but the business outcome is error reduction, measuring page views will tell you nothing about whether the design worked. Match the metric to the question, not to what's easy to pull.

**Try This:** pick a design decision you made recently. Write: "The HEART category for this is [category] because we're trying to improve [business outcome]. Before this change, [baseline]. We'll know it worked if [target]." If the baseline is unknown, that's the first finding — you're designing without a baseline.

**Proof:** A metric defined before the build can be wrong — and being wrong is the useful signal. If you set a Task Success target of 80% completion rate and land at 60%, you have a specific gap to investigate. If you define success after the fact, you'll find a way to interpret any number as reasonable. The pre-definition is what makes the measurement meaningful.

**Take this further:** in the next two weeks, check the baseline you wrote before building. Has it moved? Write one sentence: what would need to change in the design to get closer to the target?

**After you've run this yourself:** describe your design change and business goal to an AI tool and ask it to suggest a HEART metric with measurement approach — then validate whether the suggested measurement is actually accessible from your analytics setup before committing to it.

**What Next:** if you want to track signals during development rather than only after, read 135 (Leading vs. Lagging Indicators). If you want to document the metric decision for future reference, add it to your Design Decision Record using 209 (Design Decision Records).
