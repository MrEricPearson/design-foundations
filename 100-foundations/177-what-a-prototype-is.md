# What a Prototype Is
**Tier:** 100 — Recognize | **Arc:** Standalone | **Prereqs:** 103 (Attachment Is the Real Risk), 132 (Prototype Fidelity) | **Note:** Foundational for all 309 prototyping arc pieces; pairs with 178 (Prototype vs. MVP)

**Goal:** After this piece, you will be able to recognize a prototype by its purpose — answering a question cheaply before committing — rather than by how it looks or what tool made it.

**Concept:** Most practitioners carry an implicit model of how certainty is built: you design something, build it, and then find out whether it works. This sequence pays the full cost of building before finding out anything. Prototyping is the recognition that "finding out" and "building" are two different activities with two different cost structures — and that paying the finding-out cost at the cheapest possible fidelity, before paying the building cost, is almost always the better sequence.

A prototype is a disposable artifact whose only job is to answer one question cheaply. Not a miniature version of the finished product. Not a demo. Not a deliverable. A question-answering instrument that gets discarded once it has done its job. The prototype's cost is justified only by the decision it informs — which means that cost should be as low as possible while still answering the question. A prototype that costs 80% of the production build to produce is not a prototype: it has already paid most of the building cost before finding out anything.

The mechanism: the question is the prototype. Without a defined question, there is no prototype — there is only an artifact of uncertain purpose. A sketch that was built to answer "does this navigation flow make sense to a new user?" is a prototype. The same sketch built to "show leadership how the feature will look" is a demo. The artifact may be identical; the purpose determines which it is, and the purpose determines whether you learn from it.

**You'll see it when:** someone builds something — a sketch, a click-through, a piece of working code — explicitly to test whether a direction is right, not to deliver something to a user. The artifact is used to answer a question; it is not the answer itself. The question was written down before building started.

**The signal:** the team can name the question before naming the artifact. "We're building this to find out whether users understand the pricing model before they reach the checkout" is a prototype signal. "We're building something to show stakeholders what this will look like" is a demo signal. The question tells you: prototype. The showcase tells you: demo.

**Don't confuse this with a demo** — a demo shows what has been decided; a prototype tests whether a decision is the right one. The same artifact can function as either, depending on how it's used. The important distinction: when a prototype is shown as a demo before testing, it functions as a commitment signal — people in the room register "this is what we're building" and their feedback shifts from "is this the right direction?" to "how do we improve this direction?" The prototype has communicated a decision that hasn't been made yet.

**Try Noticing:** the next time someone says "let's build something to show people," ask: is this meant to answer a question, or to illustrate a decision that's already been made? What is the question? If no one can name the question — if the purpose is to show rather than to find out — it's a demo. If there's a clear question and a plan for how the artifact will answer it: that's a prototype.
