# Empty States
**Tier:** 100 — Recognize | **Arc:** Standalone | **Prereqs:** 238 | **Episode:** 9

**Goal:** Recognize when an empty state is doing work — orienting, motivating, or guiding the user — versus when it is simply absent content, so you can evaluate empty states as design moments rather than placeholder conditions.

**Concept:** The working assumption is that an empty state is what you see before content exists — a blank slate waiting to be filled. The correction: an empty state is one of the most high-value moments in an interface, because it is often the first experience a new user has of a product's actual value and the first test of whether they understand what to do next.

The mechanism: empty states occur at moments of maximum uncertainty. A user who has just signed up and sees an empty project list doesn't know what to add, whether the product will do what they need, or whether they've set it up correctly. An empty state that shows only "No projects yet" leaves all three questions unanswered and relies on the user to generate both motivation and direction. An empty state that shows what a filled state looks like, explains what the first action is and why it matters, and makes that first action available turns the moment of uncertainty into a moment of orientation.

Three distinct types of empty state, each with different design requirements:

**First-time empty:** The user has never created content. Highest uncertainty; highest risk of abandonment. The design job: demonstrate what the product does when it has content (without fabricating fake content), explain the first action clearly, and make that action available without requiring the user to navigate elsewhere to take it.

**User-generated empty:** The user has had content but deleted or moved it. Lowest uncertainty about what the product does; highest need for clarity about what happened and how to recover. The design job: confirm the state ("You've removed all items"), provide a path to restore if applicable, and make the next natural action visible.

**Search/filter empty:** The user's query produced no results. The design job: confirm what was searched or filtered, explain why nothing matched in terms of what data is available, and provide specific paths forward (modify the search, clear the filter, expand the scope) rather than dead-ending.

**You'll see it when:** New user activation rates are lower than expected despite good conversion from marketing. Users who sign up and reach the empty product state have a higher dropout rate than users who complete a first action. The empty state is the activation barrier.

**The signal:** The empty state shows a message but no available action. The design described what's missing without providing a path to create it.

**Don't confuse this with:** Onboarding. Onboarding is a deliberate orientation sequence that may appear before the empty state. The empty state is what the user encounters when the orientation sequence ends and they arrive at the product proper — and it can be the beginning of the real onboarding experience if it's designed as such. A false positive: a well-illustrated empty state with a pleasant illustration and encouraging copy feels designed. But if it doesn't answer "what do I do first?" and make that action directly available, the design work went into aesthetics rather than orientation. Check: is the first action available within the empty state, or does the user have to navigate to find it?

**Try Noticing:** Find the empty state experience in your current product for a brand-new user. Without any prior knowledge of the product: (a) Is it clear what the product does when it has content? (b) Is the first action clearly named? (c) Is that action available from the empty state itself, without navigating away? Each "no" is an orientation failure at the highest-stakes moment in the new user experience.
