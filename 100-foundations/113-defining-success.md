# Defining Success Before You Start
**Tier:** 100 — Recognize (Practice Atom) | **Arc:** Standalone | **Prereqs:** 100 | **Episode:** 2

**Goal:** Recognize when success is undefined before work begins — and write the sentence that makes it checkable rather than retroactively adjusted.

**Concept:** The working assumption is that success is recognizable after the fact — you'll know it when you see it. The correction: a success definition written after the result exists is contaminated by the result. The mechanism is hindsight bias: once we know an outcome, we retroactively construct criteria that it satisfies. A definition of success that's written after work is done will almost always validate the work, whether or not it should — because the definition is built to fit the outcome, not the other way around. A definition written before work begins can be wrong. A definition written after can't be — it adjusts to whatever happened. That asymmetry is the entire value of writing it first.

The practical consequence: retrospectives, success reviews, and "did it work?" assessments are only meaningful when the definition predates the result.

**The move:** Before starting, complete this sentence: "I'll know this worked if ___." The blank must be fillable with an observable behavior or outcome — not a feeling, not a feature shipped, not a milestone hit.

**Don't confuse success with scope.** Scope describes what you'll build. Success describes what you'll use to know if the building worked. A false positive: a detailed project plan with clear deliverables feels like a success definition — it isn't. "Ship the redesigned onboarding flow" is a scope statement. "I'll know this worked if new user activation improves within the first session" is a success definition. Both are useful; only one can be wrong after the fact.

**Try Noticing:** Look at something you're currently working on. Can you write "I'll know this worked if ___" in a way that could be checked and be found false? If the blank produces a feeling ("it feels better") or a deliverable ("we shipped it"), rewrite it as a behavior or outcome you could observe.
