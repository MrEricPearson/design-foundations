# Q3 Prototyping Enablement — Project Context

This file orients any AI assistant (or human) picking up this project. Read this first before touching any content in `01-drafts/`.

## What this project is
A Q3 goal: a platform-wide Prototyping microlearning series (Teams + SharePoint), plus one interactive talk per specialist chapter (Product Managers, Custom Dev, Non-Custom Dev/3rd party). Over the course of planning, this expanded into a much larger goal: **a full atomic-to-systems design foundations manual** — not a complete end-to-end design course, but a solid practitioner foundation across research, craft, facilitation, and AI-assisted workflows.

## Who this is for
**Functional/practitioner workers ONLY.** No leadership content, ever — not even as a separate track. If a piece requires organizational authority to act on (budget decisions, org structure, headcount), it does not belong in this series and should be cut, not just deprioritized.

## The real (unstated) purpose — for context, never surfaced in content
Two goals, in priority order:
1. **Primary:** teach people to do this themselves, building appreciation for the practice through doing it.
2. **Secondary:** let them know design is available to help when it gets hard.

Design should function as a **partnership amplifier** — designers embedded in squads can focus where they uniquely add value when practitioners handle routine design thinking themselves. AI closes the "onboarding a designer costs more than doing it myself" gap; practitioners who can self-serve on lightweight work free embedded designers for high-leverage contribution.

This framing stays entirely under the hood. The surface-level goal of every published piece is simply: teach something the reader can use today.

## Org context this content quietly responds to
- Org is agile but wants deep AI integration everywhere. AI adoption is now **mandatory** — non-adoption has real consequences. **The content stays completely silent on this mandate.** That message belongs to leadership through separate channels. Eric's role here is providing resources and training, not enforcing anything — people can take it or leave it at their own peril.
- Design is engaged haphazardly across teams — sometimes early-through-delivery but tapering before benefits show, sometimes only as last-resort firefighting, often fading in/out entirely. No universal assumption that design is "part of the process" holds.
- Core perception problem: design is seen as a barrier/weight — "by the time I onboard them, I could've just done it myself."
- Dev teams have wide latitude on HOW they work, pride themselves on building "experiences," but validate mostly through demos framed as seeking approval ("love our stuff, please?") rather than real testing.
- Work is frequently delayed by lack of requirements — the same underlying barrier as AI adoption (both need foundational clarity to function) — but teams tend to restart repeatedly rather than build that clarity first.
- Few teams stay engaged post-MVP; work moves into Hypercare, often run by a 3rd party.
- PM audience perceptions to quietly counter (documented in primary research with 16+ PMs): "Design can't help with SaaS or third-party software"; "Design is only UI polish, not substantive problem-solving"; "Design doesn't use data-driven decision making"; "Design doesn't work with vendors"; "Design can't help solve complex business problems." Future PM-targeted content should address these without naming them.

## Tone rules (non-negotiable)
- **First-person, peer/practitioner voice** — "here's what I tried," never authoritative or talking down. Modeled on a respected dev publishing a how-to on AI orchestration, not a designer lecturing the org.
- **No illustrative examples, anecdotes, or invented stories in published content.** This was explicit, repeated feedback — examples read as calling out real situations and are a "danger zone." Present information directly instead.
- Content never references the AI-adoption mandate or its consequences.

## Format (three templates — one per tier)

Every piece is **under 5 minutes** and delivers **exactly one goal**. Format differs by tier because each tier targets a different cognitive outcome.

### Tier 100 — Recognize template
`[Goal]` (recognition verb: notice / identify / name / recognize / spot) → `[Concept]` (1-2 sentences: what this is and why it matters) → `[You'll see it when]` (the situation that makes this concept visible) → `[The signal]` (one checkable sign this concept is at play) → `[Don't confuse this with]` (1 sentence: the adjacent concept most often conflated with this one, and how to tell them apart) → `[Try Noticing]` (observational prompt — look for it in something already in front of you) → `[What Next]` (conditional routing)

**Absent from Tier 100:** Method, Artifact, Proof, Watchout, AI path, Take This Further. Elements that serve practice (production) are extraneous at the recognition tier and add cognitive load without supporting the learning goal.

**Practice Atom subtype:** Some Tier 100 pieces have a single lightweight step where the doing IS the concept (e.g., HMW reframing, squint test, assumption-labeling). These use: Concept → [single-step Method] → Don't Confuse This With → Try Noticing → What Next. Three or more steps with a shareable artifact = re-tier to Tier 200.

### Tier 200 — Practice template
`[Goal]` (application verb: run / produce / apply / write / map / conduct) → `[Prior Knowledge Hook]` (1 sentence activating existing schema before new content arrives) → `[Trigger]` (when to use this method) → `[Concept]` (1 sentence: why this method works — the mechanism) → `[Method]` (exact, unambiguous steps) → `[Artifact]` (the tangible output) → `[Watchout]` (one failure mode — honest and specific) → `[Try This]` (5-minute productive practice with current work) → `[Proof]` (AFTER Try This — Mode B calibration: "if you notice X, it worked") → `[Take This Further]` (deferred spaced practice: "in the next [2-5 days]... afterward, write one sentence: [reflection prompt]") → `[AI path]` (optional — "after you've run this yourself: [one sentence acceleration]") → `[What Next]` (conditional routing)

**Key structural rules:** Proof must follow Try This — arriving before it functions as preview, not feedback. Take This Further is the spaced practice element; its reflection prompt should match the piece's learning type (application → "what would you do differently?"; schema-update → "what didn't fit?"; synthesis → "what would you tell someone doing this for the first time?"). AI path is always framed as post-attempt — never as a substitute for the method. Where Take This Further is shared publicly in a designated channel, include: "If you share it in [channel], you'll see what others noticed too."

### Tier 300 — Orchestrate template
**Arc-level header:** `[Goal]` (judgment verb: decide / adapt / judge / orchestrate / navigate) → `[Arc trigger]` (when this whole system applies)

**Per-part format:** `[Part heading]` → `[Concept]` (what this part adds that previous parts didn't) → `[Method]` → `[What you end up with]` → `[Proof]` (brief signal) → `[Watchout]`

**Arc-level footer (after all parts):** `[Try This]` (one action with current work exercising the arc as a whole) → `[Take This Further]` (week-long application + reflection prompt) → `[Judgment Exercise]` (arc-specific: "You're in [situation where the arc's key assumption fails] — what would you change, and what would you cut?") → `[What Next]`

**Judgment Exercise authoring standard:** Name the arc's key assumption. Name the situation where that assumption doesn't hold. Write the question around that specific failure case — not a generic "when wouldn't you use this?" A well-formed Judgment Exercise is arc-specific enough that the same question couldn't apply to a different arc.

**Micro-learning filters (apply before publishing):** Does it deliver something applicable today? Does it work with no prerequisite knowledge — or are prereqs explicitly named upfront? Is it completable in under 5 minutes? Does it close with a clear action? If any answer is no, either cut it or break it into its own arc.

## Sequencing philosophy
**There is no single correct order.** Discovery-to-solution, delivery-to-discovery-to-solution, and everything in between are all valid depending on context. The arcs and standalone pieces are a **pattern library** — tools to reach for based on the risk in front of you — never a mandated pipeline. `14-ordering-guide.md` gives a recommended default publishing sequence based on real prerequisites, but it is a recommendation, not a rule, and every piece stands alone if read out of order.

## The core underlying model
Everything in this manual ultimately teaches one thing: **derisking through assumption-awareness.** The foundational arc ("The Risk in What You Assume") establishes that jumping straight to code (or any starting point) is fine — the actual risk is *emotional attachment* to a direction, not where you start. Four tools reduce that risk, and every other arc in this project is a deep-dive on one of them:

- **Visibility** → Story Mapping in Cursor
- **Recognizing bias** → From a Vague Ask to a Real Persona
- **Iteration** → Mocking and Testing an Agent Handoff
- **Co-creation** → Running One Workshop, Start to Finish

## Content structure (tiered)
Content is organized by both **content complexity** and **learner maturity state**:

- **Tier 100 — Recognize:** atomic concepts, no prerequisites. After reading, you can notice this concept in real situations. One thing to understand.
- **Tier 200 — Practice:** methods with named steps and a concrete artifact. Builds on Tier 100 foundations. After reading, you can run this method with something you're working on today.
- **Tier 300 — Orchestrate:** multi-part arcs for judgment-heavy, multi-method workflows. After completing, you can apply this system to novel situations and make decisions at the seams. Each arc part is self-contained; the arc as a whole follows a Bloom's progression (Recognition → Differentiation → Application → Judgment → Synthesis).

**AI Integration across tiers:** AI appears at all three tiers differently — as a concept (Tier 100: piece 147), as a production tool (Tier 200: optional `[AI path]` element in each method), and as a design challenge (Tier 300: arc 308, Designing for AI Trust). AI decouples execution complexity from judgment complexity; the library teaches the judgment layer that AI amplifies.

See `10-master-outline.md` for the complete tiered list with every dependency mapped, and `14-ordering-guide.md` for the prerequisite table and recommended publishing phases.

## Separate track: Chapter Talks
**Async format** (all three Q3 talks are async, published to SharePoint/Teams): **Cold open (real pain from the partnership scenario) → one Method explored deeply → the real result from running it → Your turn (async exercise prompt — concrete enough to attempt in one work session with no setup) → Pull-through to library.** Three chapters: Product Managers, Custom Dev, Non-Custom Dev (3rd party).

Development process per talk: **Partnership** (find a representative with an active real problem; confirm sharing consent; two candidates per chapter in case one falls through) → **Execution** (run the method with the real scenario; document what it revealed) → **Synthesis** (write the talk using the real output as evidence) → **Publish** (link to audience-specific Start Here meta-piece; track readership, pull-through, and exercise completion).

The talk's "Your turn" exercise must be concrete enough for a practitioner to attempt in their next work session with no setup. Generic prompts ("try this with something you're working on") fail — the prompt must name the specific artifact or situation this chapter type would already have in front of them.

## Content Craft Rules (Non-Negotiable)
These rules apply to every piece drafted in this project. They are extracted from `meta/content-strategy-spec.html`. When writing any content, apply all of them without being asked. Run the Phase 1 checklist mentally before returning any draft.

### Voice — the wall rule
The discipline (design) is invisible in every piece. Never argue for design; argue for better work. Any sentence implying the reader is doing something wrong fails before it reaches them. The author is a peer sharing something useful — not a function making a case, not an expert lecturing.

### Reader relationship — the trust model
The reader's buy-in depends as much on liking the author as on understanding the content. Write like a smart friend who's figured something out and wants to share it — not like someone filing a report. This means:
- **Waste words on warmth.** Asides, self-aware moments, small admissions ("this took me a while to notice") — these aren't inefficiencies. They're the thing that makes a reader feel like a person is talking to them.
- **Invoke excitement, not just understanding.** The goal isn't just to inform. It's to make the reader want to try this. Write toward that. A reader who's excited will use what they learned. A reader who's informed might not.
- **Make it real to them.** Use "you're building something right now" not "teams often face." The reader should feel like this piece was written for their specific situation, not for a hypothetical practitioner.
- The more the reader likes the author, the more they trust the content. Personality is a feature, not a distraction.

### Structure — narrative over template
Template section elements (Concept, Signal, Don't Confuse, Try Noticing) are author checklists — they ensure completeness. They are NOT reader-facing headers. The piece should read as one cohesive narrative, not a checklist with labels on it. Bold section titles make a piece feel cold and formulaic. Use `---` breaks and narrative transitions to carry the reader through. When published on SharePoint, the visual design (blue panel, amber block) does the navigation work. In the source markdown, the structure is invisible — it lives in the prose.

### Word count — write toward five minutes
Target ~1000 words. Short is not a virtue. Compressing toward brevity strips personality and forces precision over warmth. There is no room for a human voice at 400 words. Pieces should be long enough to breathe — to include the aside, the second example, the moment where the prose slows down and sits with something. Under 700 words is a sign the piece was compressed, not crafted.

### Plain language — familiarity over precision
If a phrase requires the reader to parse it, it failed. Use the words people actually say at work. "Defending a decision" not "holding a direction." "You've put work into this" not "you've invested in it." "Wrong" not "invalidated." If you wouldn't hear it in a normal conversation, rewrite it. Technically correct language that feels clinical loses readers. Familiar language that's slightly imprecise wins them.

### Anti-AI: Banned words — never use
delve, tapestry, testament, illuminate, paradigm, intricate, multifaceted, nuanced, juxtapose, endeavor, quintessential, burgeoning, ubiquitous, synergistic, pivotal, paramount, navigate (metaphorical), embark, realm, landscape, nestled, leverage, facilitate, optimize, catalyze, holistic, robust, seamless, foster, comprehensive

Avoid: crucial, notable, significant, innovative, transformative, impactful, actionable, scalable, actually, certainly, essentially, ultimately

### Anti-AI: Banned openers and closers
Never open with: "Let's dive in" / "Let's explore" / "It's important to note" / "It's worth mentioning" / "At its core" / "In essence" / "Fundamentally" / "Generally speaking" / "In many cases"
Never close with: "In conclusion," / "To summarize," / "And that's why this matters"
Never use: "Certainly!" / "Great question!" / rhetorical Q+A ("What does this mean? It means…") / parallel negation ("Not X, but Y" — state the Y directly)

### Anti-AI: Structural bans
- Em dash: never two in the same sentence; never two in adjacent paragraphs — replace extras with a period, comma, or colon. Visual proximity matters more than word count.
- Semicolons: almost never — replace with a period
- Bold: max two instances per piece, genuine emphasis only
- Tricolons framed as profound: "clarity, simplicity, and purpose" — avoid. Anaphora (repeating "the reasons... the reasons...") also banned unless the reader is already deeply invested.
- Bullet soup: 3+ bullets with identical openers → convert to prose
- Dangling analysis: ", highlighting the importance of…" → cut

### Sentence rhythm (burstiness)
- At least one sentence of 6 words or fewer per 150 words — force this even when nothing short wants to appear
- Never three consecutive sentences within 5 words of each other in length
- Contractions throughout: "don't" not "do not"
- One idea per sentence — the "and" test: if it carries two ideas, split it

### Verbs
Kill: serves as, allows for, helps to, enables, supports, facilitates, functions as — replace with the thing they point at.
Target: breaks, reveals, forces, earns, kills, costs, surfaces, catches, names — verbs that do things.
Cut modifiers: very, quite, highly, extremely, somewhat, rather, fairly, largely — find a stronger word instead.

### Vocabulary
Every design-coded term gets plain-language handling or is cut. Key translations:
- user research → talking to users / finding out what people actually do
- ideation → brainstorming / generating options
- design thinking → never use
- design sprint → describe the process, not the brand
- human-centered design → never use
- pain points → what's frustrating / what's slowing them down
- how might we → what if we… / what would it take to…

When a precise term is needed, drop it into context so the context defines it — never define formally. Second person throughout: "you," not "teams" or "practitioners."

### Opening lines
Open in the moment — no warmup, no announcement. Goal section: declarative, no announcement. Concept: open with the situation that makes it visible, not a formal definition. Method: start the process imperatively. Watchout: name the failure mode directly without softening first.

### Goal lines and subtitles — name the experience, not the concept
The subtitle and goal line's job is recognition, not description. If the reader thinks "yes, that's me" — it worked. If they think "okay, so this article is about X" — it didn't. Name the feeling or the moment, not the mechanism. "Honest feedback on it starts to feel personal" works because it names an experience. "It gets harder to be honest about whether it's working" describes a concept. The concept is what the piece teaches. The subtitle is what makes someone decide to read it. Test every goal line: does it name something the reader has felt, or something the author wants to explain?

### Sourcing mechanic
Sources use APA inline citation format: name in the sentence + year in parentheses. "Barry Staw (1976) showed this..." or "(Kahneman & Tversky, 1979)" when name isn't in the sentence. This is the format used by Coursera, edX, and LinkedIn Learning — signals verifiability without feeling academic. Every piece needs at least 3 real sources woven into the content. Each source should appear where it earns the most trust — not batched at the end. Full citation details go in the Sources block at the end.

### Fluidity — the read-aloud test
Read the piece aloud before returning it. If the narrator stumbles, something's wrong. Fluidity means:
- Intentional rhythm: build momentum with longer sentences, then release with a short one. "Nothing else changed." lands as a beat.
- Strategic pauses: a short sentence after a dense paragraph lets the idea settle.
- Strategic awkwardness: a deliberately plain or blunt phrase can hit harder than a polished one.
- If three consecutive sentences feel like they have the same weight and pace, break the pattern.

### Humor
Every piece gets one genuine moment of humor or levity unless the subject is too serious for it. Not a pun, not a setup-and-label ("this might sound funny but") — actual humor that earns a smile. It should come from something true and recognizable. Parentheticals work well: "(If you've ever done X and felt Y, you've experienced this exact thing.)" The more the reader laughs, the more they trust the author.

### Section rules that frequently fail
- Proof must follow Try This — not precede it (a Proof before Try This is a preview, not feedback)
- AI path always framed post-attempt: "after you've run this yourself…" — never as a substitute
- Watchout: personal register, honest, specific to this method's actual failure mode — not generic caution
- Try This: names a specific artifact the reader already has. Never: "try this with something you're working on" — name the thing
- Take This Further reflection prompt must match learning type: application → "what would you do differently?"; schema-update → "what didn't fit?"; synthesis → "what would you tell someone doing this for the first time?"
- Judgment Exercise (T300 only): arc-specific. Tests the arc's key assumption failing. Must be unanswerable by a different arc.

### The cut test
Remove this sentence: does the piece lose something that can't be recovered from context? If no — cut it. Restatement of previous sentence → cut. Transition without new content → cut.
