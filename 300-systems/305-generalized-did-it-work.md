# Generalized "Did It Work" Follow-Up Habit
**Tier:** 300 — Orchestrate | **Arc:** Standalone | **Prereqs:** 113 (defining success), 209 (decision records), 210 (retrospective — the earlier, lighter version of this check)

**Goal:** After this piece, you will be able to run a structured post-launch check that produces a checkable answer — not a vague feeling — about whether something worked.

**Trigger:** some time has passed since you shipped or decided something, and nobody's checked whether it actually did what it was supposed to.

**Method:** go back to your stated success definition (or Design Decision Record). Check it against what actually happened. Write down the honest answer, even if it's "not really."

**Artifact:** a short, honest check-in on a past decision, done on a set cadence rather than never.

**Proof:** "Did it work?" checked against a pre-written success definition has three possible answers: yes, no, or can't tell. All three are more useful than the default outcome of never asking, which produces no answer at all and lets bad assumptions calcify quietly.

**Watchout:** this is the step most likely to quietly get skipped across everything in this series — it needs a reminder or habit trigger, not just good intentions.

**When no success condition was written:** If you're running the check and find no pre-existing success definition, don't skip the check — reconstruct. Write your best current recollection of what success was supposed to look like, label it "reconstructed success condition," and check against that. A reconstructed check is less reliable than a pre-written one, but it has two useful side effects: (1) it surfaces whether the goal was ever genuinely clear, and (2) it produces a record you can use as a baseline for the next decision. After running a reconstructed check, read 113 (Defining Success) before the next build starts.

**Try This:** name one thing you shipped in the last 60 days that had a stated success condition. Pull it up. Answer: did it work? If the honest answer is "can't tell," that's information — it means the success condition was too vague to be checkable.

**Take this further:** in the next two weeks, run this check on a different decision from the same period. Write one sentence: is "can't tell" appearing more than once — and if so, what does that pattern say about how success is being defined before work starts?

**Judgment exercise:** You're trying to run the check and realize no success condition was ever written — you're checking against your memory of what the goal was. The method depends on a pre-existing definition to check against. Does the check still have value without one? What does it become? What do you do first, and what can you preserve from the original intent?

**What Next:** if the check shows the success condition wasn't measurable after the fact, read 217 (UX Metrics) to define HEART targets before the next build starts. If the pattern is decisions not being documented in the first place, read 209 (Decision Records) to start the habit upstream.
